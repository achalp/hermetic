# Hermetic in August: an analysis room for your agent

Hermetic is an open-source, local-first AI data analyst I've been building in public. Its founding constraint is unchanged: the model writes the analysis code, but it never sees your data. July's update closed on the idea of budget-aware investigations. August went somewhere else first, because a door opened that was worth walking through: Hermetic is now an MCP server. Any agent that speaks the Model Context Protocol — Claude Desktop, Claude Code, or anything else — can use Hermetic as its analysis room. Your agent asks; your data stays home; the dashboard outlives the chat.

## Why bolt an analyst onto an agent that already analyzes

The obvious objection deserves to go first. Claude Code already reads CSVs, writes pandas, retries its own errors, and emits charts. Hundreds of run-a-SQL-query MCP connectors already exist. If Hermetic-as-MCP were just "let Claude analyze your CSV," it would be dead on arrival — and if usage ever shows it being used mainly as a database connector, I've written that down as the kill signal.

What survives that scrutiny is exactly what the rest of Hermetic is made of. When an agent freeforms its way through your data, rows routinely end up in the model's context — a `head()` here, a printed DataFrame there — and with a cloud-hosted agent, that means your records are transmitted to a model provider as a side effect of asking a question. Hermetic's tools return schema, statistics, and computed aggregates instead, and the code that touches your data runs in the same governed sandbox as always. The second survivor is durability: an agent chat is write-only memory, and its output is a snapshot. Hermetic's output is a persisted analysis — spec, code, schema, and artifacts — that is still there, still interactive, and still refreshable tomorrow. And the third is scale: a multi-billion-row warehouse question is one tool call, answered by pushdown, not by dragging data into a context window.

## What the agent gets

Eight tools. The flagship is `analyze`: the full Hermetic pipeline — code generation, pre-execution review, sandboxed execution, dashboard composition — invoked as a single call, returning a summary, the computed numbers, the cost, and a link. Around it sit primitives for when the agent wants finer control: `connect_source` handles every source the web app does (CSV, Excel, GeoJSON, local Parquet files and folders, cloud Parquet URLs on S3/GCS/HTTPS, saved warehouse connections), `get_schema` returns the rich statistical schema so the agent never needs to sample rows to understand a dataset, `run_sql` executes read-only SELECTs against warehouses, `run_analysis` runs the agent's own Python in the sandbox, `verify_narrative` checks every number in the agent's prose against actually-computed values, and `persist_dashboard` turns an agent-authored spec into a permanent entry. Each source announces up front which tools it supports, so the agent discovers capabilities by reading, not by being refused.

The dashboard link deserves its own sentence. The MCP process embeds a small viewer — the same renderer, the same themes, the same fonts as the web app, served loopback-only — so the link an agent hands you works with nothing else running. This month that viewer reached full visual parity: the four themes, dark mode, and Geist typography all came across, so a dashboard looks the same whether the web app or an agent asked for it.

There's one more consequence worth naming: Claude Desktop and claude.ai users have never been able to run Hermetic before — no local execution, and built-in analysis means uploading your data with size limits. With MCP, the desktop app becomes a Hermetic front end, and the existing subscription-login transport means there's still no API key involved.

## Trust, precisely: the host is a harness

Wiring an LLM-driven agent to tools that touch your data forces you to say exactly what you trust. The framing that finally made everything fall into place came out of a design conversation mid-month: Hermetic is a set of libraries composed by interchangeable harnesses — the web app is one, the CLI is another — and an MCP host is simply the third, with its tools acting as RPC into those libraries. What makes this harness different is that its logic isn't code I audited; it's a model's runtime decisions, and its context may carry injected instructions from documents or web pages it has read.

So the guards sit on authorship, not on data. SQL the agent writes passes a code-level read-only gate before any connector sees it. Python the agent writes executes with networking denied unconditionally — not as a heuristic, as a constant — while Hermetic's own generated code keeps the softer policy it earned. Dashboard specs the agent writes are validated against the component catalog in enforcing mode, where Hermetic's own specs keep the app's warn-only policy. Prompt injection lands, if it lands anywhere, in authored code — and that's where the controls are.

The month's most satisfying hardening closed the one path I'd documented as a known residual. When Hermetic's pipeline analyzes a cloud dataset, that code legitimately needs the network — and "needs the network" used to mean the open internet. Now the analysis container joins an internal Docker network with no outbound route at all, and its only door is a Hermetic-owned proxy that forwards exclusively to the hosts of the bucket being analyzed. Anything else fails closed. CI proves this on every push, including a permanent exfiltration canary: an origin that must never receive a request, checked with a positive control proving it was reachable in the first place, so silence means blocked rather than broken. When I mutation-tested the proof by deliberately weakening the allowlist two different ways, both weakenings failed the build — one of them caught only by the canary.

## The claim I had to give up

Here is the month's honest admission. The first version of this server withheld things from the agent in the name of the data boundary — per-record chart series trimmed to samples, identifier columns' values hidden from schema responses. It felt principled. It was incoherent, and it took a blunt question during dogfooding to see it: we don't hide rows from the browser, so why hide them from this harness? The agent is simultaneously the author of the queries and the recipient of the results; it can always request rows explicitly through its two sanctioned doors. Withholding them elsewhere protected nothing — it just made the agent work harder for the same outcome, while letting me pretend the return shapes were a security control.

So the claim is now precise instead of comfortable. The data plane stays local: files, sandbox, warehouse connections, dashboards, viewer. The control plane is the host, and everything a tool returns crosses into it. If your host is a cloud assistant, results reach that provider — that's a property of the host you chose, not something Hermetic can undo by hiding fields. What Hermetic owes you is that the crossing is bounded (every row-bearing response is capped), visible (every call lands in an audit log with sanitized arguments — code and queries as truncated previews, presigned-URL credentials stripped), and honestly described. Credentials never cross on any path. And if you want nothing to leave the machine at all, run a local-model MCP client; the tools behave identically. The old claim is amended in the project's own spec rather than quietly rewritten — the reasoning should outlive the conversation that produced it.

## An RPC surface owes its caller some manners

Treating the tools as RPC predicted a set of gaps a chat interface never feels. Errors are now a closed taxonomy of machine-readable codes alongside the human-readable message — an agent that sees `source_expired` can re-attach and retry without a human reading prose; when a source's data does expire, the error names the source, the cause, and the exact call that re-attaches it. Truncation is flagged, never silent: a schema response tells you it capped columns and by how many. The surface carries a contract version, so a host can tell which shape it's talking to. Long `analyze` runs stream progress notifications — stage by stage, with percentages when the sandbox reports them — so an agent can show a live status line instead of a silent multi-minute wait. None of these are features; all of them are the difference between a tool an agent can drive reliably and one it can only poke at.

A self-review of the whole flow before merge turned up fourteen findings worth fixing, including two real correctness bugs and one credential leak — a presigned URL's signature would have been written verbatim to the audit log. That last one is the reason audit sanitization now has its own tests.

## The landscape, briefly

The strongest open-source neighbor, Wren AI, pivoted its entire company this year to exactly this posture: tools and skills for agents over a governed core. I take that as validation of the direction, and the lanes remain complementary — semantics in, execution and artifacts out. Against the sea of database-connector MCPs, the distinction is the one this whole post has been circling: they move your data into the conversation; Hermetic moves answers into the conversation and keeps the analysis alive afterward.

## What comes next

July's close still stands: investigations that know their budget and weigh whether the next step is worth it. The MCP work adds its own queue — exposing the component catalog as a resource so agents can author dashboards natively (deliberately deferred until the untrusted-spec hardening is complete), tools for managing scheduled refreshes, and an investigate-mode tool. The kill-signal telemetry will decide the rest: if agents treat Hermetic as a database connector, that thesis dies; if dashboards persist and get revisited, the analysis room is real.

If you wire Hermetic into your agent and it does something useful — or something embarrassing — I'd like to hear about it.
